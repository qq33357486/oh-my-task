# 默认工作流 · SOP

> 状态：正式（2026-11-24；来源：10-工作效率反思.canvas「最终构想」；验证案例：redesign-oh-my-task，2026-11-24 人类验收通过）。
> 边界：只管一个任务从提需求到归档；拷问技法（怎么问）归 grill-with-docs 技能，本 SOP 不加规定，只写问出什么、结果落到哪；某类业务的步骤归 `.omt/工作流/` 里对应业务的那一份。
> 上下游：上游＝人类的一句话需求；下游＝`openspec/specs/` 并回后的需求、归档的任务夹、更新后的 `.omt/`。

## 名词

| 词 | 指 |
|---|---|
| 任务夹 | OpenSpec 的一个变更，即 `openspec/changes/<任务名>/` |
| 项目规则 | 项目根的 `AGENTS.md` 及它引用的文件，不含 `.omt/` |
| 新开的 AI | 新开的会话或子代理；只给它要读的文件路径，不转述做的 AI 的理解 |
| 编排工具 | 把多步交给多个 AI 自动跑的工具，如动态工作流 |
| 验收用例 | 验收场景里的一条，能程序化验收；不能的留给人亲手验 |
| 关键验收用例 | 人确认过自己最关心的验收用例，用例名前带「[关键]」，最后必须通过 |
| 开发失败 | 回做次数用完，仍有带标签的用例不通过；按失败交给人调整 |

## 框架文件

框架文件由 DJTASK 的初始化置入、更新管理，业务项目里只读：本文件、`.omt/AGENTS.md`、`.agents/skills/` 下的三个拷问技能，以 oh my task 仓库的框架名单为准。

业务项目里的 AI 发现默认工作流本身有问题（缺一步、照着做出错），不在本项目里记任何东西，只在最终汇报里说明「这是 DJTASK 的问题」。要改，由人向 DJTASK 提需求，维护者在源头走任务流程改。

## 流程

### 一、需求阶段（要人）

1. **读已有的**（AI）：读 `openspec/specs/`、`.omt/术语/`、`.omt/知识库/`、项目规则。
2. **拷问**（人＋AI，主会话）：人明确要求拷问的（说法不限，比如「请拷问我」；在认技能的工具里打了 `/grill-with-docs` 也算），必须拷问；人明说不要拷问的，不拷问。人没有明确要求的，由 AI 判断，不先问人要不要：简单的需求不拷问，直接建任务夹，不转关键验收用例；需要问清楚的，直接开始拷问。只按 grill-with-docs 做（不管是怎么触发的），不单独用 grilling。三份技能文件不靠斜杠命令：先读 `.agents/skills/grill-with-docs/SKILL.md`，照它做；它让你再加载的 grilling 和 domain-modeling 两份，有 Skill 工具就调 Skill 工具加载，没有就直接读文件，路径在 `.omt/AGENTS.md`「要拷问时」那一条里。拷问要留痕：术语和长期决策当场写，每条需求带出处；没拷问的任务，每条需求同样带出处。审查说需人信息、回到这一步时：拷问过的接着拷问，没拷问的不再问要不要拷问，直接问人那一件。下面从「另外」起到这一步结尾的话只管拷问的任务。另外要问出人想要什么：做完之后人看到什么、能做什么；人说的可能不是全貌，没说出来的也问出来，问哪里由 AI 判断。从中挑出最重要的，转成能程序化验收的验收用例，不逐条等比提炼，数量不设上下限。收尾时在对话里每条一行列给人确认，不另成文档；人改了的当场增删、转好再给看，人确认后才往下走。人确认过的才带标签，就是关键验收用例；人没明说确认的不算确认，不带标签；人自己要求加的那条也一样，转好、人看过确认之前不带标签。
3. **建任务夹**（AI，用 OpenSpec）：拆任务就在这一步。写需求与验收场景、设计和待办清单，每条需求带出处。人确认过的用例写进验收场景，和其他用例在一起，用例名前加「[关键]」，每条带出处，规矩与需求相同。转的先后：能自动测的先自动测，其次由新开的 AI 用工具验；转不了的留给人亲手验，不打标签，写明为什么转不了。回做次数在这一步定，写在任务夹里。待办清单的最后一条固定是「固定新东西并填核对单」；人类验收和归档不算待办，写在清单后面的 Workflow follow-up 里。写完当场把「AI 假设」单子问完；没答完的，不得送审。
4. **独立审查**（新开的 AI）：对照任务夹（连待办清单一起审）、项目规则、`openspec/specs/` 和 `.omt/术语/` 里已有的东西，按下表分流。带标签的用例和它的出处、留给人亲手验的用例也在审查范围内，多核两项：带标签的用例对不对得上出处里人想要的，有没有只验了一部分、或验的是别的东西；转不了、留给人的，是不是真的转不了。

| 审查结论 | 去向 |
|---|---|
| 通过 | 进第二阶段 |
| AI 错误（写错、漏了、没出处；带标签的用例转偏了；能验的说成转不了） | AI 改任务夹，回到第 4 步 |
| 需人信息（只有人知道） | 回到第 2 步 |

审查通过即等于人已说开始，AI 直接进第二阶段。

### 二、执行阶段（人只推动，不审文档）

1. **读**（AI）：读项目规则、相关系统的需求、这类业务的业务工作流。
2. **做**（AI）：逐项做，做完一项勾一项。发现漏问的（有一样人该会关心、之前没人问到）不停下：只转用例、只验，标「AI 假设」，不去实现任务夹里没有的事；人答「是」之前不带标签，不通过不算开发失败。做完的汇报里列：每条带标签用例通过与否和依据、留给人亲手验的几条、执行中新加还不带标签的用例（单独一节，每条写通过与否；不通过的由人决定加不加进任务夹）。
3. **测**（AI）：按任务夹里的验收场景测。
4. **独立验收**（新开的 AI）：对照任务夹和项目规则核。

用编排工具跑的，只有人点名才启动。业务工作流里标了「（要人）」的步骤，停下等人。

| 哪一步不过 | 去向 |
|---|---|
| 自动测试不过 | 回到「做」 |
| 独立验收不过 | 回到「做」。执行中新加、人还没答的用例不通过不算独立验收不过，不进这一行。带标签的用例不通过也回「做」；回做次数用完仍不通过，按开发失败交给人，写明哪条没通过、为什么。人调整后，需求要改的交回需求阶段，做法要改的交回执行阶段，回做次数由人重新定 |

**卡住**＝自己能查、能试的都用完了，剩下的只有人能定。卡住就停下，等人类推动。

### 三、整理归纳阶段（人验收）

1. **固定新东西**（AI）：按下面「固定新东西」逐项做，填核对单。
2. **人类验收**：看做的结果，一并确认「要人确认的只有两样」。人亲手过留给自己的那几条，带标签的看结果；执行中新加的用例在这里一并答是或否，答「是」的补上标签。不通过，交回执行阶段；需求本身要改，交回需求阶段。
3. **归档**（AI，用 OpenSpec）：需求并回 `openspec/specs/`，任务夹进归档。归档后把 `openspec/specs/` 里的出处行去掉，出处留在归档的任务夹里。理由：出处行离开任务夹就看不懂；以后改一条需求时，旧的出处行还会被抄进新的任务夹。

## 固定新东西

每种新东西的去处只有一个，按表做。

| 新东西 | 怎么认 | 落到哪 |
|---|---|---|
| 需求 | 系统今后该怎样，长期有效 | 任务夹的需求文件；归档时并回 `openspec/specs/` |
| 术语 | 项目里一个词的固定叫法和含义 | `.omt/术语/GLOSSARY.md` |
| 长期决策 | 难改回去，别人看了会问为什么 | `.omt/术语/ADR/` 一条一个文件 |
| 踩过的坑 | 这次出错后纠正的做法 | 出错的那份业务工作流的「常见错误」。是默认工作流本身的问题，业务项目里不写，见「框架文件」 |
| 流程缺步骤、新类型的任务 | 现有工作流里没写的步骤，或没有对应文件的业务类型 | 新增或修订 `.omt/工作流/` 里的业务工作流。缺的步骤在默认工作流里，业务项目里不写，见「框架文件」 |
| 知识 | 以后用得上的项目资料 | `.omt/知识库/` |
| 项目规则 | 要改项目根 `AGENTS.md` 或它引用的文件 | 项目规则文件 |

**谁写**：AI 写。术语和长期决策在拷问当时写（没拷问的任务在这一步写），其余在这一步写。

**核对单**（必填，写进任务夹的 proposal.md 末尾）：

```text
需求：有／无 → 文件路径
术语：有／无 → 文件路径
长期决策：有／无 → 文件路径
踩过的坑：有／无 → 文件路径
项目规则：有／无 → 文件路径
流程缺步骤或新类型：有／无 → 文件路径
知识：有／无 → 文件路径
```

## 要人确认的只有两样

项目规则、`.omt/工作流/` 里的流程。其余的新东西，AI 按上表直接落。

这两样先写好，人类验收时不确认就撤回。

## 规则

- 人只出现在：答拷问（含答「AI 假设」单子、收尾时确认关键验收用例）、业务工作流标明的节点、卡住时推动、人类验收、开发失败时调整。
- 每条需求的标题下第一行以「> 出处：」开头，内容二选一：人类的原话，或「AI 假设」加编号。标「AI 假设」的汇总成一张单子，人类只答是／否；答「是」的，出处改成人类的原话。
- 交接只认任务夹；新会话用 `openspec list` 找未归档的任务夹，接着做。
- 单次性的结论不固定；预期以后还要用的才落。

## 强制

1. AI 的假设必须标明，人类答了是才算定。
2. 已经写在 `openspec/specs/`、`.omt/术语/` 里的，不许再问；要改由人类先提。
3. 需求稿每条必须带出处；没有出处的不得进入审查。
4. 开工前必须读项目规则；实现不得违背项目规则。
5. 独立审查、独立验收必须由新开的 AI 做；做的 AI 不得自审、自验。
6. 独立验收不过，不得交人类验收。例外：按开发失败交给人，交的时候明说是失败的（见下面第 9 条）。
7. 归档前必须做完「固定新东西」并填好核对单。
8. 归档必须由人类验收通过触发。
9. 带标签的用例最后必须通过；回做次数用完仍不通过，按开发失败交给人。

## 禁止

1. 禁止把拷问放进编排工具；只在主会话做。
2. 禁止人类在拷问之后到人类验收之前审文档。
3. 禁止人没点名就自行启动编排工具。
4. 禁止为让测试通过而改测试或改需求。
5. 禁止在整理时新加或删减本次任务夹里的需求；归档并回 `openspec/specs/` 除外。
6. 禁止往 `openspec/` 里放 OpenSpec 以外的文件。

## 常见错误

| 现象 | 修正 |
|---|---|
| 把问过的问题又问一遍 | 第一步先读完已有内容 |
| 需求里混进 AI 自己加的东西 | 每条查出处的；查不到的标「AI 假设」 |
| 审查不过就回到拷问，把人类拉回来 | 只有「需人信息」才回拷问，其余 AI 自己改 |
| 写任务夹的 AI 顺手把审查也做了 | 审查另开新 AI |
| 悄悄少做，汇报时说做完了 | 做不完的明说哪块没做、为什么 |
| 卡住了硬猜 | 停下问人 |
| 这类任务没有对应的业务工作流，就凭感觉做 | 先问人类，走通后沉淀成业务工作流 |
| 任务做完，定下来的东西只留在对话里 | 「固定新东西」逐项做，填核对单 |
| 每次任务都往规则里加一条 | 单次性结论不固定 |
| 拷问了很多轮，却没问人想要什么 | 问出人想要的，转成用例给人确认 |
| 把能验的说成转不了，推给人 | 独立审查核这一项 |
