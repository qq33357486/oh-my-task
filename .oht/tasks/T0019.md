## 需求
### round 2（2026-11-03 人看 round 1 后当面定案）：环形布局 + 默认视图 + 自适应居中
1. 环形布局：五环节首尾相接成一个环（需求→测试→实现→检查→记录→需求），不再横排；「检查→实现」「记录→需求」两回边自然融入环形连线，不再单独画弧。
2. 流程图为默认视图：页眉切换控件「流程图」排最前，进入页面默认展示流程图；看板仍可切换查看。
3. 自适应居中：整页固定、无横向滚动；左右清单+中画布在窗口内自适应，常规最大分辨率（如 4K）下画布居中、大小合适，无需手动调整（允许设最小分辨率下限）。
4. 布局定案：左=两层清单（收件箱、未开始两区）；右=单层清单（归档）；中=环形画布（节点可携带信息）。
5. 可读性：节点、清单、连线上的文字大小与对比度须清晰可读（人重点强调）。
6. DOM 契约 data-flow-* 保留；连线语义变化（回边融入环）致既有断言不适者，按批准变更同步改写并注明（先例 T0004/A4）。

### round 1（2026-11-03 人批 B 定案）：ComfyUI 式深色网格画布
1. 画布区重做为节点编辑器形态：深色底 + 网格点阵；五环节 = 五个实体大节点（圆角深色面板、标题栏、端口圆点），卡以行挂节点内部（编号+标题+知识标签+轮次徽标不变）。
2. 连线改贝塞尔端口线：环节顺序连线 + 「检查→实现」「记录→需求」两回边，随节点位置实时更新；流光粒子保留（深色底上沿边流动）。
3. 画布交互：空白处拖拽平移、滚轮缩放、节点可拖拽重定位（位置存内存即可，不持久化）。
4. 左右清单（收件箱/未开始/归档）改为画布上同风格实体面板，整体全画布化；DOM 契约 data-flow-* 全部保留（data-flow-view/node/card-id/inbox/todo/archive/tag/edge）。
5. 看板视图保持亮色不变；页眉切换不变。
6. 既有 11 锁定用例的 DOM 断言预期零改动；实现结构调整致个别断言不适时，按批准变更同步改写并注明（先例 T0004/A4、T0007）。

### round 0 遗留（布局语义与清单规则仍有效；呈现技术以 round 1 为准）
给网页系统新增第二个视图「流程图」：以循环工程环节为节点，把当前所有任务卡在流程上的位置画出来。人一眼看到"现在哪些卡在哪个环节、哪些卡要我拍板"。

### 布局（人已确认）
- 左侧清单，分两区：上部「收件箱」= need_human 卡（醒目，复用 T0016 模式直显 question/stop_reason）；下部「未开始」= status=new 卡。
- 右侧清单 = status=recorded 已归档卡。
- 中间画布 = 循环工程五个环节节点（不是状态码）：需求 → 测试 → 实现 → 检查 → 记录。
- 卡片挂到当前状态对应的环节：new→需求、tests→测试、ready→实现、review→检查、done→记录。
- 回边（SVG 弧线）：检查 → 实现（检查不通过打回）；记录 → 需求（循环闭合）。
- need_human 卡不占中间画布（人已拍板留在左侧收件箱，属人已确认的映射）。

### 卡面
- 复用现有卡面范式（T0017 极简）：小编号 Tag + 人话标题。
- 知识标签：卡的 type 有对应 knowledge/topics/<type>.md 且文档含「标签」字段时，卡面显示该标签文字（≤4 字）；无文档或无字段则不显示。
- round>0 的卡显示「第N轮」徽标（实现-检查往返次数）。
- 点卡交互与看板一致（弹层全文渲染）。

### 流光动效（人已确认 SVG/CSS 方案）
- 有卡挂着的环节节点高亮；流程边上出现流动光点/流光描边动画，表达"循环在转"。

## 候选教训
- 实现员（2026-11-03，T0019 round 2）：vitest 默认不应用 CSS（jsdom 中样式表不生效），类选择器控制的 `display:none` 在组件测试里等于没写——`toBeVisible/not.toBeVisible` 判的是内联 style 与祖先链计算样式，而 jsdom 里 CSS 类规则恒缺失。适用条件：vitest + jsdom 下做「CSS 隐藏式互斥可见」或任何依赖样式表生效的 DOM 断言。症状：类名加上了、测试仍报 Received element is visible。规避：可见性切换走内联 `style.display`（jsdom 与真实浏览器两侧一致）；若必须走样式表，需在 vitest 配置里显式开 `css` 并评估代价。
- 实现员（2026-11-03，T0019 round 2）：`getBoundingClientRect()` 返回含自身 transform 的视觉盒——用它做「容器内容 fit/居中」计算时，元素已有的 scale 会混入尺寸测量（本卡实测：初始 scale 0.7 下 rect 356×304，布局盒实为 712×608，fit 结果系统性偏移 122px）。适用条件：对带 transform（或将被 transform）的元素测量以驱动布局计算。症状：fit/居中结果与手算不符，偏差恰等于初始缩放因子。规避：布局计算读 `offsetWidth/offsetHeight`（不含 transform 的布局盒）；getBoundingClientRect 只用于「屏幕坐标锚定」类场景（如滚轮缩放的指针锚点）。
- 实现员（2026-11-03，T0019）：jsdom 24 没有 PointerEvent 构造器（jsdom 25 才加入），@testing-library fireEvent.pointerDown/Move 回退普通 Event，clientX/clientY/button/pointerId 全部丢失，仅事件类型与冒泡可用。适用条件：jsdom<25 组件测试模拟 pointer 拖拽/坐标类交互。症状：`e.button !== 0` 这类守卫把 button=undefined 的事件全拒之门外，拖拽静默失效。规避：button 守卫放行 undefined（仅明确非主键才拒绝）；坐标逻辑用 Number.isFinite 判可用性并备无坐标降级路径（如固定步进）；测试断言只锚「值变化」不锚具体 delta（本卡检查员测试已如此写，天然兼容降级）。
- 实现员（2026-11-03，T0019）：AntD Button 对恰好两个汉字的 children 自动插空格（「看板」渲染成「看 板」），children 包 span 也挡不住（该版本递归文本检测），getByText 精确匹配即挂。适用条件：AntD 按钮 + 锁定精确文本断言（jsdom 或真实 DOM 同理）。规避：改原生 button 自绘样式，或 ConfigProvider button={{ autoInsertSpace: false }}（后者全局生效，需评估既有「刷 新」类两字按钮形态与测试）。
